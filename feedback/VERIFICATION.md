# 실제 Supabase 연결 검증

## 5차 수정 검증

- HEIC 피드백 화면은 확인을 위해 로컬 PNG로 디코딩했으며 공개 자산이나 온라인 저장소에 올리지 않았습니다. 화면의 시계/주소창은 Safari UI입니다. 가져오기의 iOS 소스 선택 메뉴도 브라우저가 제어합니다.
- 새 랜딩 원본은 `assets/reference/landing-v5.svg`에 보관했습니다. 실제 사용한 다섯 경로와 순서가 일치하고, SVG 프레임의 네 모서리가 8개 모바일/PC 뷰포트의 모서리에 맞음을 확인했습니다. 프레임을 너비·높이에 각각 맞추므로 가로 화면의 그래픽 비율은 변합니다. 랜딩 14/24/27px·Home 제목 28px 고정, PC Home 버튼 최소 28px를 확인했습니다.
- `tests/design_browser.py`는 기존 4차 테스트를 현재 요구에 맞게 갱신한 파일입니다. PC 7가지 크기의 실제 회전 글자 경계, Photo/Fin의 가로 중앙·상단 정렬, 왼쪽 위 Back, 느려진 화살표 이동과 기존 PNG/날짜/사진 비가림 검증을 통과했습니다. 아카이브 내부 세로 스크롤은 허용합니다.
- Processing 8개 파일은 4차 수정 직전 `6c11c83`의 파일과 SHA-256이 같습니다. 막대·패턴 그래픽으로 복원하고 생성 스크립트에서 이 자산을 덮어쓰지 않도록 했습니다.
- `tests/revision5_browser.py`: 긴 세로 사진의 원본 비율·화면 내 버튼 유지, 세로 상세 사진만 4:5 cover 크롭·가로 사진 contain 유지, 원본 사진 비율 보존, 정확한 Arrow 4/1 경로와 실제 다음 게시물 이동, Fin INFO 제거를 확인했습니다.
- 효과음의 정규화된 PCM은 유지하되, 아이폰도 AudioBufferSourceNode로 재생합니다. 터치 컨텍스트에서 실제 버퍼 구간의 최대 진폭이 0.5를 넘고 여러 구간이 재생됨을 관찰했습니다. 아이폰용 무음 미디어 루프는 별도로 구분해 상태와 소스 유지·강제 일시정지 없음만 확인했습니다. 실제 AudioContext suspend 후 사용자 탭에서 running과 음성 구간 재생이 재개됨을 확인했습니다.
- Web Audio가 없는 환경에서는 실제 AAC 대체 요소가 0.35초 이상 재생하고 자연스럽게 ended에 도달함을 확인했습니다. 짧은 JS 타이머로 강제 정지하지 않습니다. 새 AAC 파일은 원본 타격음의 정규화된 WAV에서 만들었습니다.
- 위 브라우저 검증은 시스템 Chromium과 아이폰 사용자 에이전트/터치 에뮬레이션입니다. 실제 iPhone Safari의 청취를 확인하지 못했습니다. 추가 WebKit 엔진 다운로드는 이 환경의 네트워크 정책이 HTTP 403으로 차단했습니다. 사용자에게 확인한 결과 무음 모드 해제·미디어 음량을 올린 상태에서도 이전 재생 방식에서는 소리가 나지 않았습니다.
- 모바일 회귀 10개 화면, 실제 PNG 두 장 다운로드, IndexedDB 보존, 모의 Supabase 저장/재시도/공개 조회와 색 분석 4개 테스트를 통과했습니다. 이번 검증에서 실제 Supabase에 새 결과를 업로드하지 않았습니다.
- HTML·JS·CSS·랜딩/처리 프레임에 5차 버전을 반영했습니다. 공개 배포는 기존 `/feedback/` 경로이며 익명 HTTPS 검사는 랜딩과 모든 새 AAC 파일의 해시·오디오 MIME도 검사합니다.

## 4차 수정 검증 (기록)

- `tests/revision4_browser.py`: 1024×768, 1280×720, 1366×768, 1440×900, 1920×1080, 2560×1440, 1366×500에서 PC 글자 확대·로고 왼쪽 정렬·Info 최대 1080px와 본문 확대·Photo/Fin 버튼의 동일 위치/크기와 세로 간격을 확인했습니다. 320×480, 390×844, 844×390에서도 아카이브 목록/상세의 제목 위치와 크기가 홈과 일치함을 확인했습니다.
- PC 사진 배경 화살표 3개의 실제 애니메이션 좌표가 화면 너비/높이를 넓게 이동하며 이전보다 빠른 주기를 갖고, 동작 줄이기에서는 멈춤을 확인했습니다.
- 첨부 화살표 7개 원본을 보존했고, Arrow 3은 사용자가 마지막에 선택한 Arrow 4의 세로 반전입니다. 새 PNG를 만드는 실제 SVG의 8개 경로와 변환, 처리 프레임의 경로가 원본과 일치합니다. 랜딩은 앞서 지정한 별도 원본 구도입니다. 이미 저장된 결과 파일에는 소급 적용하지 않습니다.
- 새 포스터의 실제 픽셀에서 날짜 스탬프가 작아지고 오른쪽 위로 이동하여 하단 행사 정보와 간격을 확보함을 확인했습니다. 화살표 조합은 원본 경로를 모두 같은 비율로 축소하고 위치를 조정했습니다. 사진은 타이포 중앙 정렬 변환에서 분리해 원래 위치에 두고, 실제 SVG 사진 레이어의 변환된 영역을 측정해 가려지는 화살표 픽셀이 없음을 확인했습니다. 새 파비콘 SVG와 PNG/iOS 아이콘, 10-10 링크 제거, 새 한글/영문 크레딧과 행사명을 확인했습니다.
- 기존 WAV들의 RMS를 측정하니 약 -47~-80dBFS로 매우 작았습니다. 전체 MP3를 먼저 PCM으로 디코딩한 후 추출·페이드·피크 정규화하여 8개 모두 약 -24~-27dBFS, 최대 진폭 0.85이며 무음 구간으로 잘못 잘리지 않았음을 검증했습니다. 파형 샘플과 구간 사이의 무음을 직접 검사합니다.
- 아이폰 사용자 에이전트·터치 컨텍스트에서 실제 미디어의 재생 시간, 반복 `playing` 이벤트와 다른 구간으로의 이동, 소스/요소 재사용을 확인했습니다. HTTP Range가 없는 로컬 서버에서도 내려받은 Blob의 탐색을 사용합니다. 실제 iPhone Safari 하드웨어의 청취 확인과 구분합니다.
- 기존 10개 화면의 모바일 회귀, 실제 두 PNG 다운로드, 로컬 저장·아카이브, 모의 Supabase 실패/동일 경로 재시도·익명 세션·게스트 조회 검사를 통과했습니다. 병렬 업로드 요청의 도착 순서는 보장하지 않으므로 재시도는 세 경로의 집합으로 비교합니다. 이번 테스트에서 실제 서비스에 새 결과를 저장하지 않았습니다.
- 공개 배포는 기존 `/feedback/` 주소를 사용하며 Pages 빌드와 인증·쿠키 없는 HTTPS 파일 해시 검사를 확인합니다. 앱에 추가 빌드 의존성이나 SQL 변경은 없습니다.

## 3차 수정 검증

- 한글 전체 KoPubWorld Medium(500), 뷰포트 전체 너비의 배경, 원본 랜딩의 잘리지 않는 `meet` 배치, 늘어난 Info 행간을 10가지 화면 크기에서 확인했습니다.
- 새 PNG는 1200×1500px(4:5)입니다. 실제 생성 SVG의 타이포 그룹 외곽에 변환을 적용한 중심이 프레임 중심과 일치함을 검증했습니다. 이전 저장분의 파일은 수정하지 않았습니다.
- 아이폰 사용자 에이전트·터치 컨텍스트에서 실제 HTML 오디오 요소의 재생 시간이 진행되고, muted=false·volume=1·오류 없음과 요소 한 개의 재사용을 확인했습니다. 녹음의 8구간을 WAV로 추출했습니다. 이 검증은 실제 iPhone Safari 하드웨어에서의 청취 확인과 구분합니다.
- 사진 선택은 사이트 메뉴 없이 사용자 클릭에서 기본 파일 선택기를 여는 것을 확인했습니다. iOS의 시스템 소스 메뉴 자동 선택은 지원할 수 없습니다.
- 아카이브 상세의 캡션·날짜 설명·저장 버튼 제거, 팔레트 8색의 불투명 배경, 이전/다음 이동과 목록 복귀를 확인했습니다.
- 로컬 키 커서로 인접 게시물을 읽고, 모의 온라인 70건의 첫/마지막·배치 경계·오래된 직접 링크에서 올바른 인접 ID를 제한된 요청 수로 찾음을 확인했습니다. 추가 SQL이나 전체 테이블 공개 없이 기존 목록 RPC를 사용합니다.
- 공개 배포의 `/feedback/` 하위 경로에서도 브라우저 회귀를 실행합니다. 공개 링크와 배포된 파일의 일치는 생성된 GitHub Actions의 익명 HTTPS 검사로 따로 확인합니다.
- 당시 Pages 원본 변경 API가 HTTP 403으로 거절됐으나, 이후 사용자가 `codex/public-feedback`으로 선택을 완료했습니다. 스냅샷 `a35761c`의 Pages 빌드와 `Public feedback anonymous access` 검사가 모두 성공했습니다. 이후 수정본은 같은 브랜치에 새 스냅샷을 배포합니다.

## 이전 모바일 수정본 검증 (기록)


- `node --test tests/core.test.cjs`: 색상 분석 4개 테스트 통과.
- `python3 tests/smoke.py http://127.0.0.1:8002`: 320×480부터 1440×900까지 10개 화면에서 랜딩·홈·사진·완성·Info·다운로드 메뉴의 화면 경계/내부 콘텐츠 크기 검증 통과. 아카이브는 요청에 따라 영역 내부 스크롤을 허용합니다. 긴 세로 사진 축소, 사진-버튼 간격, 2초 컬러 전환, 800ms 결과 교대, PNG 두 종류 동시 다운로드, 동작 줄이기를 확인했습니다.
- 실제 Playfair Display 500 Italic/Panchi Mono 로드 및 Canvas 날짜 그리기를 확인했습니다. 이후 사용자 요청으로 한글은 제공된 KoPubWorld 바탕으로 우선 대체했습니다. 헤드라인은 Medium(500), 작은 글자·본문은 Light(300)입니다.
- KoPubWorld 두 파일을 WOFF2로 변환하고 전체 25,971개 문자 매핑과 글자 폭 보존을 확인했습니다. 브라우저의 실제 렌더링 폰트를 검사해 제목은 `KoPubWorldBatangMedium`, 본문·작은 문구는 `KoPubWorldBatangLight`로 표시됨을 확인했습니다. 서체 변경으로 가로 화면의 하단 페이지 화살표가 넘치던 부분은 해당 화면에서 글자 크기를 줄여 맞췄습니다.
- 제공된 MP3의 8개 타격음 구간 재생 호출과 진동 API 호출을 확인했습니다. 새 수정에서는 첫 사용자 동작 이후 호버/키보드 조작과 Processing 프레임 전환의 효과음도 확인했습니다. 초기 랜딩에는 자동 진동 호출이 없습니다. 실제 청취·진동의 세기/느낌은 테스트하지 않았습니다. iOS Safari 웹 진동과 기본 사진 소스 메뉴 강제 생략은 지원할 수 없습니다.
- 랜딩 3.6초 낙하, 상단 영문 정체, INFO의 Pretendard Regular·호버 색상 제거, Home 아카이브 칸 위치·동일 세로 간격, Info 양끝정렬·영문 정체, Fin 3개 버튼의 같은 폭을 확인했습니다.
- 첨부 SVG의 8개 뒤로가기 모양이 1초 간격으로 실제 전환되고, 동작 줄이기에서는 멈춤을 확인했습니다.
- 공개 아카이브의 4:5 카드·사진 cover, 호버/누르고 있기 미리보기, 탭 시 사진·궤적의 좌우 상세, 12→24→31개 스크롤 추가 로드, 최신순 정렬·중복 없음, 상세 복귀 시 스크롤 보존, IndexedDB v1→v2 기존 결과 보존을 로컬 브라우저에서 확인했습니다.
- 두 PNG의 브라우저 다운로드는 각각 1206×1560px이며 내용이 다름을 확인했습니다. 네이티브 공유 API는 iPhone 사용자 에이전트의 모의 구현에서 사용자 활성 상태를 유지한 1회 호출로 PNG 2개를 전달함을 확인했습니다. 공유 취소 시 메뉴 유지와 재시도 가능도 확인했습니다. 실제 iPhone 사진 앱에 두 장이 저장되는지는 별도 기기 확인이 필요합니다.
- `python3 tests/archive_browser.py http://127.0.0.1:8002`: 모의 REST로 세 파일 업로드 실패·같은 경로 재시도·익명 세션 재사용/갱신·게스트 조회·공개 아카이브를 확인했습니다. 서버나 실제 정책 검증으로 간주하지 않습니다.

- 화면 캡처로 모바일 세로·가로 레이아웃을 점검했습니다. 실제 휴대폰의 Safari/Chrome 검증은 별도입니다.

이후 실제 `list_trajectories` 조회가 HTTP 200으로 응답하여 [supabase/archive.sql](supabase/archive.sql)이 적용됐음을 확인했습니다. 로컬 개발 서버의 새 브라우저에서 실제 Supabase 공개 목록, 사진·궤적 파일, `get_creation` 상세를 읽어 모두 HTTP 200·좌우 표시·페이지 오류 없음으로 확인했습니다. 이 조회는 아래와 같은 검증된 HTTPS 전달 방식이며 응답을 모의 처리하지 않았습니다. 이번에는 로그인이나 업로드·데이터 수정 요청을 보내지 않았고 새 테스트 자료를 만들지 않았습니다. 실제 배포 URL의 기기 검증과는 구분합니다.

- 해당 브라우저에서 실제 Storage 사진·궤적 로드: 각각 HTTP 200.
- 해당 브라우저에서 실제 Storage 포스터 다운로드: HTTP 200, PNG 1206×1560px 확인.
- 일반 방문자의 결과 테이블 직접 목록 조회: HTTP 401로 차단.
- 브라우저 페이지 실행 오류 없음.

검증 브라우저는 이 개발 환경의 프록시 인증서를 직접 신뢰하지 못했습니다(`ERR_CERT_AUTHORITY_INVALID`). 브라우저의 API 요청을 시스템 인증서 검증을 유지하는 Python HTTPS 경로로 전달하고 **실제 Supabase 응답**을 돌려주는 방식으로 검증했습니다. API 응답을 모의 처리하지 않았고 TLS 검증을 비활성화하지 않았습니다. 이 검증은 실제 휴대폰의 직접 접속/카메라/공유/효과음/진동 검증을 대신하지 않습니다.

기존 로컬 브라우저·모의 REST 테스트와 별도로 수행한 실제 서비스 검증입니다. 운영 중인 Vercel 사이트 배포는 실행하지 않았습니다. 직접 앱 URL에서의 운영 검증은 배포 후 수행합니다.

## 검증 자료 정리

실제 검증에는 개인정보가 없는 합성 8색 사진을 사용했습니다. 이미지 3장, 결과 행 1건과 익명 계정 1개가 생성됐습니다. 현재 앱 권한에는 삭제가 없으므로 자동 정리는 하지 않았습니다. 비공개 관리자 키를 요청하지 않습니다.

운영자가 Supabase 콘솔에서 다음 순서로 정리할 수 있습니다.

1. **Storage → trajectory-images**에서 사용자 폴더 `c0a10c2d-5bfb-4b79-af9c-69d8a6671045`를 엽니다.
2. 그 안의 결과 폴더 `f0c58992-7050-44be-89c3-ada50ae0db73`에 있는 `photo.jpg`, `arrows.png`, `poster.png`를 선택해 삭제합니다. 다른 결과 폴더는 지우지 않습니다.
3. **Table Editor → creations**에서 `id`가 `f0c58992-7050-44be-89c3-ada50ae0db73`인 행만 삭제합니다.
4. 필요하면 **Authentication → Users**에서 ID `c0a10c2d-5bfb-4b79-af9c-69d8a6671045`인 테스트 익명 계정도 삭제합니다.

이미지 삭제는 Storage 화면에서 진행합니다. SQL로 `storage.objects` 행만 직접 지우면 실제 파일이 정리되지 않을 수 있습니다.
